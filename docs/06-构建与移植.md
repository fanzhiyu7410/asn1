# 构建与移植

## 1. 构建系统基线

- 构建工具：CMake ≥ 3.20，生成器不限（Ninja、Makefiles、Visual Studio、Xcode 均可）。
- 实现语言：C++17；公共头文件为 C99。
- 仓库为**多包布局**：根 `CMakeLists.txt` 编排核心 `asn1`、`modules/` 下的独立标准模块与 `tools/asn1c`；每个包有独立版本与安装导出。
- 库不依赖第三方运行时；核心不使用异常、RTTI、标准 IO、线程库。
- 许可证：MIT，见仓库根目录 `LICENSE`。

## 2. 目标与产物

| CMake 目标 | 所属包 | 类型 | 导出名 | 产物（Windows / Unix） | 用途 |
| --- | --- | --- | --- | --- | --- |
| `asn1_shared` | `asn1` | SHARED | `asn1::shared` | `asn1.dll` + `asn1.lib` / `libasn1.so`、`libasn1.dylib` | 常规动态集成 |
| `asn1_static` | `asn1` | STATIC | `asn1::static` | `asn1_static.lib` / `libasn1_static.a` | 静态链接、嵌入式、无共享库场景 |
| `asn1_pkix_shared` | `asn1-pkix` | SHARED | `asn1::pkix::shared` | `asn1-pkix.dll` / `libasn1-pkix.so` | 标准结构模块（一期） |
| `asn1_pkix_static` | `asn1-pkix` | STATIC | `asn1::pkix::static` | `asn1-pkix_static.lib` / `libasn1-pkix_static.a` | 模块静态链接 |
| `asn1_pkcs_shared` / `asn1_pkcs_static` | `asn1-pkcs` | SHARED / STATIC | `asn1::pkcs::shared` / `asn1::pkcs::static` | 同名规则 | 标准结构模块（二期第一批，只读） |
| `asn1_cms_shared` / `asn1_cms_static` | `asn1-cms` | SHARED / STATIC | `asn1::cms::shared` / `asn1::cms::static` | 同名规则 | 标准结构模块（二期第二批，只读） |
| `asn1c` | 工具 | EXECUTABLE | 无 | `asn1c` / `asn1c.exe` | `.asn1` 解析与描述表生成 |

核心目标由 `ASN1_BUILD_SHARED`、`ASN1_BUILD_STATIC` 控制，至少启用一个。模块目标同时受全局 `ASN1_BUILD_MODULES` 与各自的包级开关控制；模块只链接核心目标，核心不链接任何模块。工具 `asn1c` 不链接核心或模块，独立安装到 `bin/`。

共享库与静态库使用不同输出名，避免 Windows 导入库与静态库同名覆盖。

## 3. 选项矩阵

| 选项 | 默认值 | 作用 | 备注 |
| --- | --- | --- | --- |
| `ASN1_BUILD_SHARED` | `ON` | 构建 `asn1::shared` | 与静态库可同时开启 |
| `ASN1_BUILD_STATIC` | `ON` | 构建 `asn1::static` | 嵌入式常用 |
| `ASN1_BUILD_MODULES` | `ON` | 构建 `modules/` 下标准模块 | 关闭后三个包级开关全部失效 |
| `ASN1_BUILD_MODULE_PKIX` | `ON` | 构建 `asn1-pkix` | 仅 `ASN1_BUILD_MODULES=ON` 时生效 |
| `ASN1_BUILD_MODULE_CMS` | `ON` | 构建 `asn1-cms` | 仅 `ASN1_BUILD_MODULES=ON` 时生效 |
| `ASN1_BUILD_MODULE_PKCS` | `ON` | 构建 `asn1-pkcs` | 仅 `ASN1_BUILD_MODULES=ON` 时生效 |
| `ASN1_BUILD_TOOLS` | `ON` | 构建 `tools/asn1c` | 工具不链接核心或模块 |
| `ASN1_BUILD_EXAMPLES` | `OFF` | 构建 C 与 C++ 消费示例 | 示例只使用公共 C ABI |
| `ASN1_BUILD_TESTS` | `OFF` | 构建测试并注册 CTest | 当前为无第三方框架的最小 C 用例；doctest 待登记后引入 |
| `ASN1_BUILD_EMBEDDED_TEST` | `OFF` | 构建嵌入式最小用例 | 可独立于 `ASN1_BUILD_TESTS` 开启，交叉编译时只构建不运行 |
| `ASN1_BUILD_BENCHMARKS` | `OFF` | 构建批量基准 | 不进 CTest 主流程；需要 `asn1-pkix` 目标 |
| C++ 异常 | 固定关闭 | `-fno-exceptions` / `/EHs-c-` | 无缓存开关（已确认的硬约束） |
| C++ RTTI | 固定关闭 | `-fno-rtti` / `/GR-` | 无缓存开关（已确认的硬约束） |
| `ASN1_FREESTANDING` | `OFF` | 定义 `ASN1_FREESTANDING=1`，裁剪宿主依赖 | 必须配合自定义分配器或静态池 |
| `ASN1_WARNINGS_AS_ERRORS` | `OFF` | 告警视为错误 | CI 的“严格”构建启用 |
| `ASN1_ENABLE_SANITIZERS` | `OFF` | ASan + UBSan | 仅宿主调试构建；MSVC 不支持该组合 |
| `ASN1_CXX_STANDARD` | `17` | 内部 C++ 标准 | 允许 `20`，基线只验收 `17` |

**异常与 RTTI 没有开关**：构建脚本固定传入 `-fno-exceptions -fno-rtti`（MSVC 为 `/EHs-c-`、`/GR-`，并定义 `_HAS_EXCEPTIONS=0`）。这是已确认的硬约束，不提供“打开异常”的选项。

## 4. 常用构建命令

```bash
# 配置（宿主平台默认生成器）
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug

# 构建
cmake --build build

# 构建并运行测试（启用测试后）
cmake -S . -B build -DASN1_BUILD_TESTS=ON
cmake --build build
ctest --test-dir build --output-on-failure

# 本地安装
cmake --install build --prefix out/install

# 只构建核心（不构建模块与工具）
cmake -S . -B build-core -DASN1_BUILD_MODULES=OFF -DASN1_BUILD_TOOLS=OFF
cmake --build build-core
```

模块与工具默认开启；`ASN1_BUILD_SHARED` 与 `ASN1_BUILD_STATIC` 至少需要一个，模块会按同名库类型链接对应核心目标。

Windows + Ninja + MinGW 的显式写法：

```powershell
cmake -S . -B build -G Ninja `
  -DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++ `
  -DCMAKE_BUILD_TYPE=Debug
cmake --build build
```

## 5. 安装与消费

安装布局（相对前缀）：

| 路径 | 内容 |
| --- | --- |
| `include/asn1/` | 核心公共 C 头文件（含生成的 `asn1_version.h`） |
| `include/asn1/pkix/`、`include/asn1/pkcs/`、`include/asn1/cms/` | 各模块公共头文件（含生成的 `<模块>_version.h`，模块安装时） |
| `bin/asn1c` | `.asn1` 工具（`ASN1_BUILD_TOOLS=ON` 时） |
| `lib/`（或 `lib64/`） | 核心与模块的共享库、静态库、导入库 |
| `lib/cmake/asn1/` | `asn1Config.cmake`、`asn1ConfigVersion.cmake`、`asn1Targets.cmake` |
| `lib/cmake/asn1-pkix/` | `asn1-pkixConfig.cmake`、版本文件、`asn1-pkixTargets.cmake` |
| `lib/cmake/asn1-cms/` | 同上规则 |
| `lib/cmake/asn1-pkcs/` | 同上规则 |

核心消费：

```cmake
find_package(asn1 CONFIG REQUIRED)
target_link_libraries(my_app PRIVATE asn1::shared)  # 或 asn1::static
```

模块消费：

```cmake
find_package(asn1-pkix CONFIG REQUIRED)
target_link_libraries(my_app PRIVATE asn1::pkix::shared)
```

每个模块的配置文件通过 `find_dependency(asn1 0.1.0 CONFIG)` 自动解析对核心的最低版本依赖（模板使用构建时生成的 `ASN1_CORE_VERSION`，当前为 `0.1.0`），消费者不需要单独 `find_package(asn1)`，但也可以显式调用。

C 消费同样通过 CMake 目标：

```cmake
find_package(asn1 CONFIG REQUIRED)
add_executable(my_app main.c)
target_link_libraries(my_app PRIVATE asn1::shared)
# 静态库 + C 源文件时，CMake 需要 C++ 链接驱动：
set_target_properties(my_app PROPERTIES LINKER_LANGUAGE CXX)
```

非 CMake 工程：

- 共享库：包含 `include/`，链接 `asn1`（Windows 链接导入库 `asn1.lib`）；模块另需包含对应模块目录并链接模块库。
- 静态库：包含 `include/`，链接 `asn1_static`（Unix 为 `libasn1_static.a`），并定义 `ASN1_STATIC`（Windows 下否则 `ASN1_API` 会展开为 `dllimport`；CMake 目标 `asn1::static` 会自动传播该宏），并使用 C++ 链接驱动或确保运行时可用。
- 公共头文件不要求调用方使用 C++17；只有库内部实现需要。

### 5.1 模块对核心的版本依赖

- 每个模块在配置文件中记录其构建时依赖的核心版本范围，`find_dependency` 按该范围查找 `asn1`。
- 核心 ABI 稳定期内（同一主版本），模块可独立升级次版本，不要求与核心同版本发布。
- 模块升级若需要核心新增符号，必须在模块元数据中声明新的核心最低版本，由 `find_package` 提前失败而不是在链接期报错。
- 核心不得依赖任何模块；模块间默认互不依赖，跨模块复用通过公共 ASN.1 描述或调用方自行组合。

## 6. 平台注意点

### 6.1 Windows

- 导出宏：核心 `ASN1_API`、模块 `ASN1_PKIX_API` 等在共享库构建时展开为 `__declspec(dllexport)`，共享消费时展开为 `__declspec(dllimport)`；静态库构建与静态消费时展开为空。静态消费方必须处于 `ASN1_STATIC` / `ASN1_<模块>_STATIC` 生效状态：CMake 静态目标自动传播，非 CMake 工程需自行定义。
- 编译源文件使用 `/utf-8`，避免中文注释导致的代码页问题。
- 共享库与静态库输出名分离；安装时两者都安装。模块库名带模块前缀，避免与核心同名。
- 不依赖 MSVC 特有类型；`int64_t`、`size_t` 使用 `<stdint.h>`/`<stddef.h>`。
- 调试构建可用 `/W4 /permissive-`；发布构建不启用 `/GL`/LTCG 作为默认，避免 ABI 工具链差异。

### 6.2 Linux

- 隐藏可见性：`CXX_VISIBILITY_PRESET hidden`；仅 `ASN1_API` 符号导出。
- SONAME 由 `SOVERSION` 固定为 ABI 主版本（当前 `0`），完整版本为 `0.1.0`。
- 不链接 `pthread`、`dl`、`rt`；不依赖 glibc 扩展。
- 使用 `-fno-exceptions -fno-rtti` 时，消费者若链接静态库需自行处理 C++ 运行时；纯 C 消费者建议优先共享库。

### 6.3 macOS

- 共享库使用 `.dylib` 与 `install_name`；CMake 的 `SOVERSION`/`VERSION` 生成对应版本化文件名。
- Apple Silicon 与 Intel 均使用同一源码；CI 覆盖 `arm64` 与 `x86_64`。
- 不依赖 ObjC/Foundation；纯 C++/C 运行。

### 6.4 嵌入式 / freestanding

- `ASN1_FREESTANDING=ON` 时不使用 `malloc/new`、异常、RTTI、文件、线程、`<iostream>`、`<locale>`。
- 必须提供 `asn1_allocator_t` 或静态池；否则上下文创建返回配置错误。
- 建议关闭共享库，只使用静态库，并由链接脚本裁剪未使用符号。
- 栈使用受 `max_depth` 约束；解码优先显式栈，避免深度递归。
- 建议在目标工具链上开启 `-Os` 并关闭不必要 RTTI/异常；不要依赖主机 libstdc++ 的异常表。
- 交叉编译工具链文件：[arm-none-eabi-cortex-m4.cmake](file:///z:/work/asn1/cmake/toolchains/arm-none-eabi-cortex-m4.cmake)（`-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard`，`-specs=nosys.specs`，`--gc-sections`）。

```bash
cmake -S . -B build-arm -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/arm-none-eabi-cortex-m4.cmake \
  -DCMAKE_BUILD_TYPE=Release \
  -DASN1_BUILD_SHARED=OFF -DASN1_BUILD_STATIC=ON \
  -DASN1_FREESTANDING=ON -DASN1_BUILD_MODULES=OFF -DASN1_BUILD_TOOLS=OFF \
  -DASN1_BUILD_EMBEDDED_TEST=ON -DASN1_WARNINGS_AS_ERRORS=ON
cmake --build build-arm --parallel
arm-none-eabi-size build-arm/tests/embedded/test_embedded_pool
```

- 本机实测（Ubuntu 26.04 WSL2 + arm-none-eabi-gcc 14.2.1，Cortex-M4F hard-float，Release）：构建与链接通过；`libasn1_static.a` 121,036 字节；嵌入式最小用例 ELF 为 `.text` 11,548、`.data` 1,348、`.bss` 17,212（其中 16 KB 为用例的静态池）。链接期 newlib 会对 `_close/_lseek/_read/_write` 给出“未实现”提示（`nosys.specs` 预期行为），不影响产物。

> **静态池尺寸是“无 schema 解码下限”，不是通用上限。** 上述 16 KB 静态池只覆盖“无 schema 的 BER/DER 解码 + 构树”场景。若还要加载描述表（schema）并做 schema 感知解码，池需求会显著增加：宿主实测 `tests/embedded/test_pkix_pool`（二分求最小池，静态池 + 加载 PKIX 描述表 + 解码一张真实 RSA 自签证书）得到 **最小静态池 86,880 字节**（约 85 KB），约 16 KB 的 5.3 倍；`asn1_ctx_size_for_config` 报告的上下文固定开销为 448 字节。集成方应参照该测量为“描述表 + 证书解码”场景预留容量，并自行按目标样本压测。
>
> **嵌入式按实测分两档：**
> - **核心 BER/DER 解码（无 schema）**：`.text` 约 11.5 KB（含 `.data`/`.bss`，实测 `.text` 11,548 / `.data` 1,348 / `.bss` 17,212）、静态池 **16 KB 起**，适合小容量 MCU（本机 Cortex-M4F 交叉构建/链接 + qemu-arm 运行已实测）。
> - **带 PKIX 描述表 + schema 感知解码**：最小静态池约 **85 KB**（实测 86,880 字节），需外扩 RAM，约 16 KB 的 5.3 倍；**约 85 KB 的池不适合 RAM 低于 96 KB 的小容量 MCU**，此类场景应关闭模块/描述表，仅用核心无 schema 路径。
- 运行验证：裸机 ELF 无法在 `qemu-arm` 用户态执行；用 `arm-linux-gnueabihf` 交叉构建同一用例并在 `qemu-arm` 下运行（见第 10 节状态表）作为“无堆、静态池、池耗尽”行为的运行期证据；真实 Cortex-M4 板卡未验证。

### 6.5 字节序与对齐

- ASN.1 编码中的长度、整数、标签均为大端语义；实现显式读写字节，不依赖宿主字节序。
- 描述表是另一套字节契约：所有多字节字段显式**小端**读取，与 ASN.1 编码的大端语义无关；生成的 C 数组为 `uint8_t[]`，不映射结构体，也不要求 8 字节对齐（对齐仅作性能优化）。
- 结构体内存布局只用于内部，不跨 ABI 传递；公共结构体字段顺序固定，但不使用 `#pragma pack`。
- 分配器返回的内存至少满足 `max_align_t`；节点内容按字节访问，无未对齐读取。
- 32 位目标需保证 `size_t` 可表示输入长度；公共接口使用 `uint64_t` 表达预算，入口处检查转换。

## 8. 版本与 ABI 产物

### 8.1 唯一真源

- 核心 `project(asn1 VERSION 0.1.0)`；每个模块以自己的 `project(asn1-pkix VERSION 0.1.0)` 等声明版本，互不覆盖；`tools/asn1c` 以自己的 `project(asn1c VERSION 0.1.0)` 声明独立版本。
- 版本号只写在上述 `project(...)` 中；公共头文件、SONAME、包版本文件全部由 CMake 派生，源码树中不手写版本宏。

### 8.2 生成版本头

- 模板：`cmake/asn1_version.h.in`（核心）、`cmake/asn1ModuleVersion.h.in`（模块）与 `cmake/asn1cVersion.h.in`（工具）。
- 生成：`cmake/Asn1Version.cmake` 中的 `asn1_generate_core_version_header()` 与 `asn1_generate_module_version_header(<name>)`，以及 `tools/asn1c/CMakeLists.txt` 中的 `configure_file(... @ONLY)`，把 `PROJECT_VERSION_*` 替换进模板。
- 输出位置：核心为 `${CMAKE_BINARY_DIR}/generated/include/asn1/asn1_version.h`；模块为 `<模块构建目录>/generated/include/asn1/<name>/<name>_version.h`；工具为 `<工具构建目录>/generated/include/asn1c_version.h`（工具内部使用，不安装）。
- 暴露方式：生成目录以 `$<BUILD_INTERFACE:...>` 加入目标的 `target_include_directories`；消费者通过 `#include <asn1/asn1_version.h>` 或 `#include <asn1/<name>/<name>_version.h>` 使用。
- 安装：核心生成头安装到 `include/asn1/asn1_version.h`，模块生成头安装到 `include/asn1/<name>/<name>_version.h`；安装后与源码树头文件使用方式一致。
- 宏内容：`<前缀>_VERSION_MAJOR/MINOR/PATCH/STRING/ENCODED`；`ENCODED = major << 16 | minor << 8 | patch`。核心前缀为 `ASN1_`，模块为 `ASN1_<模块>_`。
- 生成头不包含业务逻辑，只含宏与函数声明所需的版本信息。

### 8.3 产物名与 SONAME

共享库目标统一设置：

```cmake
set_target_properties(<target> PROPERTIES
  OUTPUT_NAME <产物名>          # 核心 asn1；模块 asn1-pkix 等
  VERSION ${PROJECT_VERSION}
  SOVERSION ${PROJECT_VERSION_MAJOR})
```

- Linux：`libasn1.so.0.1.0` 为实体，`libasn1.so.0` 为 SONAME，`libasn1.so` 为开发链接名；模块同理，如 `libasn1-pkix.so.0`。
- macOS：`libasn1.0.1.0.dylib` 为实体，`libasn1.0.dylib` 为 SONAME/`install_name`。
- Windows：无 SONAME，共享库为 `asn1.dll`（模块 `asn1-pkix.dll`），导入库与静态库使用不同文件名，避免覆盖。
- 次版本升级只改完整版本，不改 `SOVERSION`；主版本升级同时改两者并视为 ABI 破坏。

### 8.4 包版本文件与模块依赖区间

- 核心与各模块都用 `write_basic_package_version_file(... VERSION ${PROJECT_VERSION} COMPATIBILITY SameMajorVersion)` 生成 `<包名>ConfigVersion.cmake`，安装在 `lib/cmake/<包名>/`。
- 模块配置模板 `cmake/asn1ModuleConfig.cmake.in` 通过 `find_dependency(asn1 <最低版本> CONFIG)` 声明所需核心的最低版本；最低版本由模块 CMakeLists 构建时从核心项目版本取得。
- 同一主版本内核心可向后兼容升级；模块若使用核心新增符号，必须抬高最低版本，让 `find_package` 在配置期失败，而不是留到链接期。

### 8.5 CI 断言

以下三项必须与对应 `project(... VERSION ...)` 一致，任一不一致即失败：

1. **生成头**：`asn1_version.h` / `<module>_version.h` / `asn1c_version.h` 的 `*_VERSION_MAJOR/MINOR/PATCH/STRING` 与 `PROJECT_VERSION*` 逐项相等。
2. **SONAME/产物名**：`VERSION` 等于完整项目版本，`SOVERSION` 等于主版本；Unix 产物 SONAME 与 `SOVERSION` 一致。
3. **包配置版本**：`<包名>ConfigVersion.cmake` 中记录的版本等于 `PROJECT_VERSION`。

配置阶段已对生成头做存在性与 MAJOR/MINOR/PATCH/STRING 逐项一致性检查（`cmake/Asn1Version.cmake` 用正则读取生成文件并与 `PROJECT_VERSION_*` 比对）；CI 在安装后补充 SONAME 与包版本文件检查。

运行时 `asn1_version_check` 只对**主版本不一致**报错，次版本差异视为兼容；CMake 包配置使用 `SameMajorVersion`，两者策略一致。能力差异通过 `asn1_version_info_t.capabilities` 与 `asn1_has_capability()` 查询，不通过次版本号推断。

核心与模块 ABI 承诺见 [C API 设计规范](02-C-API规范.md)第 11 节与 [ADR-0001](adr/0001-C-ABI边界.md)；版本一致性的决策背景见 [ADR-0010](adr/0010-版本一致性机制.md)。

## 9. 第三方依赖与许可证

- **运行库零第三方依赖**：核心 `asn1` 与 `asn1-pkix`、`asn1-cms`、`asn1-pkcs` 的 shared/static 产物只链接 C 运行库与平台系统库，不得链接任何第三方库。
- **测试与工具白名单**：仅接受 MIT、BSD-2-Clause、BSD-3-Clause、Apache-2.0（含 LLVM 例外）等宽松许可；禁止 GPL/LGPL/AGPL 或许可不明代码进入仓库。
- **登记入口**：[第三方依赖与许可证清单](第三方依赖与许可证清单.md) 逐项记录名称、版本、用途、引入阶段、许可证、来源与是否随产物分发。仓库内尚无第三方源码；doctest 尚未 vendored，libFuzzer 随编译器工具链提供。
- **检查**：`python scripts/check_third_party.py` 扫描 `include`、CMake 依赖声明、vendored 目录与 fuzzer 链接引用，未登记即失败；一期 CI 以 `deps-license` job 挂载。
- **分发合规**：`LICENSE` 维持 MIT；发版随包提供 `THIRD_PARTY_NOTICES.md`。当前无随产物分发的第三方组件，该文件保持空模板。
- **变更流程**：新增依赖先更新清单并说明许可证，再进入代码；评审同时检查清单、分发声明与实际引用。决策背景见 [ADR-0011](adr/0011-第三方依赖与许可证策略.md)。
