## 4. 逐条决策说明（Q1–Q13）

### Q1 schema 描述格式

- **是什么**：决定类型描述以什么形式交给核心，用于字段命名与约束校验。
- **为什么重要**：决定模板 API 形状，也决定模块与用户自定义类型能否共用同一校验路径。
- **可选方案与代价**：A 仅运行时注册 API，宿主代码多但最稳；B 仅二进制描述表，跨语言但需定格式与加载器；C 工具生成 C 源表，性能好但构建链变重。
- **结论**：选 A+B：核心同时提供描述表加载与运行时注册，两条入口构建同一棵类型树。描述表由 `asn1c` 离线生成，可为 C 源数组或二进制资源，带 `format_version`；核心不做文本解析。字节布局与兼容策略见[描述表格式](11-描述表格式.md)。
- **不决策后果**：模块无法携带预生成表，自定义类型与标准类型会分裂成两套实现。
- **最晚时点**：一期已确认（D12、D20）。

### Q2 `.asn1` 工具形态

- **是什么**：决定独立工具 `asn1c` 的职责边界与交付时点。
- **为什么重要**：模块表必须由工具生成，否则 `asn1-pkix` 无法在一期落地。
- **可选方案与代价**：A 只校验，成本低但无法产出描述表；B 解析 + 校验 + 生成描述表，成本中等且直接支撑模块；C 生成强类型代码，体验最好但工作量与 ABI 风险最高。
- **结论**：选 B。一期交付 MVP：解析 `.asn1` 文本、语义校验、生成描述表；一期必须支持 `IMPORTS` 与单参数参数化，`CLASS`/`WITH SYNTAX`/信息对象集以预展开模块输入；二期补跨模块增量校验、更多输出形态与直接解析评估。
- **不决策后果**：模块只能手写描述表，易漂移且无法复现。
- **最晚时点**：一期已确认（D13、D20）。

### Q3 CER 支持时点

- **是什么**：CER 是 BER 的规范化变体，主要差别是不定长与集合排序规则。
- **为什么重要**：影响后续范围与测试向量；CER 与 BER/DER 共用大量 TLV 代码。
- **可选方案与代价**：A 固定排入二期，复用现有代码；B 需求触发，避免无目标工作量；C 永不做，损失一类用户。
- **结论**：选 B，需求触发。出现明确 CER 场景时再评估，届时复用 BER 不定长与 DER 排序基础；不写入二期固定承诺。
- **不决策后果**：若固定排期，会制造无人使用的实现与测试面。
- **最晚时点**：需求出现时（D14）。

### Q4 PER/UPER 范围

- **是什么**：PER/UPER 是按模式约束压缩的编码，需知道比特位宽，强依赖类型描述与约束求值。
- **为什么重要**：工作量最大，决定是否投入约束求值与定长计算，影响整体规模。
- **可选方案与代价**：A 先 UPER，面向 5G/嵌入式；B 先对齐 PER，面向传统电信；C 暂不规划，只留扩展位。
- **结论**：选 C，暂不规划，不列入任何固定阶段。理由：证书/PKCS 生态统一使用 DER，PER 按 schema 推导位置编码，本场景不出现。
- **重启条件**：出现明确 PER 场景需求（如 5G/智能卡项目），且模式约束求值（SIZE、值域、可扩展性）与定长计算（固定部分、OPTIONAL 位图、CHOICE 索引）已就绪；重启前修订 ADR-0002 与 ADR-0009。
- **不决策后果**：无目标地铺开会让模板机制背着 PER 需求设计，拖慢一期。
- **最晚时点**：需求出现时（D15）。

### Q5 错误消息本地化

- **是什么**：决定错误文本是库内固定英文，还是按宿主语言/地区输出本地化消息。
- **为什么重要**：影响公共 API 是否引入语言参数、消息表与内存，波及 ABI 稳定。
- **可选方案与代价**：A 固定英文 + 稳定错误码，成本最低；B 库内多语言表，体积与维护上升；C 宿主按错误码自行映射，灵活且库精简。
- **建议**：选 A+C：库只给英文 ASCII 与错误码，本地化由宿主映射；符合 D7 与嵌入式裁剪。
- **不决策后果**：二期若临时加语言参数，会破坏已发布 ABI。
- **最晚时点**：二期。

### Q6 事件式/SAX 解码

- **是什么**：SAX 是边解析边回调、不建整棵树；现有方案是先建 DOM 树再访问。
- **为什么重要**：决定内存上限能力与解析器是否需第二套路径，直接影响维护成本。
- **可选方案与代价**：A 只做 DOM，最简单；B 增加 SAX 回调，超大数据友好但等于再写一套解析器；C 先做增量 feed、仍建树，折中。
- **建议**：选 A+C：二期只做增量 feed，不承诺 SAX；若嵌入式出现硬性流式需求再单独立 ADR。
- **不决策后果**：若先按 DOM 定 API，后期加 SAX 需重构解析核心。
- **最晚时点**：二期。

### Q7 大整数支持

- **是什么**：ASN.1 INTEGER 可超过 64 位，例如 RSA 公钥模数。
- **为什么重要**：决定证书/密码学场景能否直接读取，影响核心值类型 API 与测试覆盖。
- **可选方案与代价**：A 只给原始字节，成本零但用户自行解析；B 增加只读视图与十进制串，成本中等；C 内置任意精度运算，成本高。
- **结论**：选 B：只读视图 + 十进制导出，不做运算；原始字节始终保留。排在核心一期。
- **不决策后果**：模块与用户被迫在库外重复实现大整数文本化。
- **最晚时点**：一期已确认（D16）。

### Q8 时间类型解析

- **是什么**：UTCTime/GeneralizedTime 是否解析成年月日时分秒。
- **为什么重要**：影响时间校验、排序与业务接入，也决定是否依赖时区库。
- **可选方案与代价**：A 保持原样，零成本；B 只读结构化解析（含时区偏移），成本低；C 完整时区换算与格式化，成本高且平台相关。
- **结论**：选 B：结构化只读解析，保留时区偏移，不做时区归一；排在核心一期。
- **不决策后果**：模块做字段展示时还要各自解析时间字符串。
- **最晚时点**：一期已确认（D17）。

### Q9 静态池尺寸估算

- **是什么**：静态池是预先划定的固定内存，问题是给嵌入式用户可靠的容量估算手段。
- **为什么重要**：池太小会解码失败，太大浪费 RAM，直接影响 D4 的静态分配可用性。
- **可选方案与代价**：A 只给文档公式，成本低但靠人工；B 离线估算脚本，按样本统计峰值，成本中等；C 运行时自动扩容，违背静态池初衷。
- **建议**：选 B 二期提供离线脚本，输出建议池大小与余量；文档公式保留为兜底。
- **不决策后果**：嵌入式集成靠试错，二期静态池方案难以验收。
- **最晚时点**：二期。

### Q10 CI 平台与制品发布

- **是什么**：决定代码在哪个 CI 平台跑三平台构建、测试与模糊测试。
- **为什么重要**：没有 CI，跨平台与 ABI 承诺无法持续验证；也影响制品发布方式。
- **可选方案与代价**：A GitHub Actions，托管免费、矩阵成熟；B GitLab CI，适合内网；C 自建 Jenkins，灵活但运维重。
- **建议**：选 A，先跑 Linux/Windows/macOS 矩阵与 ASan、fuzz 定时任务；内网镜像后续再补。
- **不决策后果**：一期合入后无自动回归，D7 兼容承诺缺证据。
- **最晚时点**：一期 CI 接入时。

### Q11 包管理器集成

- **是什么**：除 CMake config 外，是否为 pkg-config、vcpkg/Conan 提供描述。
- **为什么重要**：影响非 CMake 接入与维护；本库已拆成核心与多个模块包，包描述需要按包分别提供。
- **可选方案与代价**：A 仅 CMake config，成本最低；B 加 pkg-config，成本低、Linux 友好；C 同时支持 vcpkg/Conan，覆盖广但维护重。
- **建议**：选 A+B：二期为核心与各模块分别加 pkg-config；vcpkg/Conan 待 ABI 稳定后再上；符合 D7。
- **不决策后果**：二期发布后再补包描述，需改安装布局与测试。
- **最晚时点**：二期。

### Q12 版本一致性机制

- **是什么**：版本号同时出现在 CMake、版本宏和运行时字符串，问题是怎样保证三者永远一致；多包后每个包各自需要一套。
- **为什么重要**：不一致会让调用方误判 ABI，直接违背 D7 的兼容承诺。
- **可选方案与代价**：A 手写头 + CI 比对，简单但易漏；B CMake 生成版本头，单一来源、成本低；C 不设宏只留运行时版本，兼容性检查变弱。
- **结论（已确认，D18）**：选 B。各包以自己 `project(... VERSION ...)` 为唯一真源，`configure_file` 生成版本头（`*_VERSION_*` 宏）到构建目录并随安装发布，源码树不手写版本宏。运行时提供 `asn1_version()` 与 `asn1_version_check()`，不匹配返回 `ASN1_E_VERSION_MISMATCH`。产物名与 `SOVERSION` 从项目版本派生，包配置用 `write_basic_package_version_file`，模块用 `find_dependency(asn1 <最低版本> CONFIG)`；CI 断言生成头、SONAME、包版本三者一致。
- **不决策后果**：一期发版即可能出现版本漂移，后期修正需改公共头。
- **最晚时点**：一期已确认（D18），详见 [ADR-0010](adr/0010-版本一致性机制.md)。

### Q13 第三方许可证审计

- **是什么**：登记项目里所有第三方代码及其许可证，避免 MIT 项目被迫附带不兼容条款。
- **为什么重要**：直接影响 D9 的 MIT 发布、商业集成与法律风险；工具 `asn1c` 可能引入语法解析依赖，需单独登记。
- **可选方案与代价**：A 只允许 doctest（MIT）用于测试，运行库与工具零第三方；B 允许 MIT/BSD 等宽松许可但逐项登记；C 不限制，最快但审计风险高。
- **结论（已确认，D19）**：选 A+B。运行库零第三方；测试与工具仅接受 MIT、BSD-2/3-Clause、Apache-2.0（含 LLVM 例外）等宽松许可，禁止 GPL/LGPL/AGPL 与许可不明代码。所有依赖登记到清单，`scripts/check_third_party.py` 在 CI 比对未登记引用并失败；发版保持 MIT 并提供 `THIRD_PARTY_NOTICES.md`。当前仓库无第三方源码，doctest 与 libFuzzer 均不随产物分发。
- **不决策后果**：一期随意引入依赖，后期替换或补授权成本高。
- **最晚时点**：一期已确认（D19），详见 [ADR-0011](adr/0011-第三方依赖与许可证策略.md)。

## 5. 处理规则

1. 任何后续阶段问题在启动前必须转为“已确认”并写入 ADR；未确认前不得实现。
2. 若发现新的阻塞一期问题，立即更新本文与[覆盖度清单](基线覆盖度清单.md)，并暂停相关实现。
3. 本清单不记录纯技术细节（如具体函数命名），后者由编码规范与评审处理。
